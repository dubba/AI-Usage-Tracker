# PureFence audit finds one conditional root escalation

**PureFence v0.2.4 contains no confirmed critical vulnerability, malicious behavior, or backdoor, and the published DMG is authentic, Developer ID-signed, hardened-runtime enabled, notarized, and stapled; nevertheless, the audit identified one High-severity shipping configuration weakness that could permit conditional local privilege escalation, three additional Medium shipping weaknesses, and material release-provenance risks.** The High finding is not a demonstrated exploit: the root helper's launchd plist has **no `SpawnConstraint`**, and the application accepts registration from a user-writable `~/Applications` bundle. If a standard user registers the helper from such a bundle and an administrator later approves it, replacing the embedded helper could potentially cause launchd to execute attacker-controlled code as root on a subsequent start. Runtime exploitation was **not verified**, and macOS may provide an equivalent implicit constraint; a disposable-VM replacement test is required before treating this as a confirmed end-to-end privilege-escalation vulnerability ([launchd plist](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/Launchd.plist#L1-L25), [registration path](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/GUI/App/HelperClient.swift#L188-L224), [Apple launch-constraint guidance](https://developer.apple.com/videos/play/wwdc2023/10266/)). The shipping XPC request boundary itself is strong, the reviewed release passed all 18 project hardening regression checks, no suspicious network destination or credential-theft mechanism was found, and the current v0.2.4 artifact's SHA-256 was independently confirmed as `97c9e7f7c0db47f97855a99c6a868940c30306178e70b64084295790ea08910f`. PureFence therefore **appears safe to run as an ordinary single-user application if obtained from the official release and installed under `/Applications`, but it should not be treated as hardened for high-risk multi-user deployments until the launch constraint, DNS response validation, and DNS resource bounds are fixed**.

## Shipping release: privileged helper and runtime weaknesses

The audited source revision was `f53cc410a10b6474daf98b9d41980e0d6c28b1aa` (2026-11-27). The table separates confirmed source-level weaknesses from conditional risks and records both exploitability limits and a concrete remediation for each finding; “confirmed” below means the code defect or mismatch is established, not that every downstream impact was dynamically reproduced.

| **L2 — Low** | **Dormant privacy-sensitive code, not an active leak.** `Sources/Shared/IPGeo.swift:3-42` defines an `IPGeoCache` actor that sends an IP to `https://ip-api.com/json/{ip}` at `:15-26`; `Sources/Shared` is compiled into both shipping targets (`project.yml:41-44,150-166`), and the endpoint string exists in both v0.2.4 binaries. | **L3 — Low / Informational** | **Shipping debug/demo switch.** `Sources/GUI/App/PureFenceApp.swift:42-68` compiles `PUREFENCE_DEMO=1`, seeds synthetic traffic/rules/country data, and skips Network Extension activation. | It changes GUI state, not root enforcement, but a production launch with the variable set can display synthetic monitoring data as if live. This is suspicious-looking but not evidence of malicious behavior. | Compile demo support only in Debug, or add an unmistakable persistent demo banner and production guard. |

The broader helper review found additional **conditional risks**, not demonstrated shipping vulnerabilities. A manually run ad-hoc root helper weakens XPC identity checking to an identifier-only requirement (`Sources/Helper/HelperService.swift:302-317`); although the shipping script requires a Developer ID authority and hardened runtime (`Scripts/sign_and_notarize.sh:42-52,100-106,127-130`), an ad-hoc root daemon should fail closed rather than accept spoofed identity (**Medium for local/ad-hoc deployments, not applicable to the Developer ID release**). Blocklist refresh reads the complete body with `URLSession.shared.data(for:)` and then converts and parses it, with only a 45-second timeout and no byte/entry cap (`Sources/Helper/BlocklistManager.swift:80-111,142-165`), creating **conditional Medium remote memory-exhaustion risk if a provider is compromised**; stream and cap bytes, lines, and entries. Legacy `/etc/pf.conf` cleanup performs a non-atomic compare-then-replace (`Sources/Helper/PFManager.swift:483-551`), creating a **Low** risk of overwriting a concurrent administrator's change; use the supported `com.apple/*` anchor mechanism or a shared lock and inode/content recheck immediately before rename. Cache reads follow symlinks and cache files are not opened with `O_NOFOLLOW` (`Sources/Helper/BlocklistManager.swift:118-140`), creating a **Low** risk if unsafe cache state pre-existed; use `lstat`/`fstat`, `O_NOFOLLOW`, and `O_EXCL`. The parent support directory is root-only (`Sources/Helper/HelperSecurityState.swift:187-205`), so these paths do not yield an unauthenticated route to root.

## Shipping controls and release evidence

The strongest compensating control is the privileged XPC boundary. `Sources/Helper/HelperService.swift:64,129,272-318` builds a release code-signing requirement pinning the GUI bundle identifier and Team ID and applies it to the privileged `NSXPCListener`; `:932-1005,1010-1031` reauthorizes each request using XPC effective UID plus persisted owner/console-administrator policy. The client connects through the privileged Mach namespace at `Sources/GUI/App/HelperClient.swift:1045-1063`. This means C1 occurs outside the request-level control—launchd launches the packaged binary before XPC authentication—while the reviewed XPC surface itself has no confirmed bypass. ([source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L272-L318))

The remaining privileged code is also unusually disciplined. No shell-based command construction was found: subprocesses use absolute executables and argument arrays for `/bin/launchctl` (`Sources/Helper/HelperSecurityState.swift:69-87`), `/sbin/pfctl` (`Sources/Helper/PFManager.swift:756-786`), `/usr/sbin/lsof`, and `/usr/bin/nettop` (`Sources/Helper/NetMonitor.swift:160-173,310-323`). PF rule interpolation is constrained to validated IPv4/CIDR/port tokens (`Sources/Helper/PFManager.swift:223-307`; `Sources/Shared/Models.swift:132-215`), avoiding hostname/PF injection. The privileged SQLite restore path uses `lstat`, `O_NOFOLLOW`, descriptor `fstat`, owner/type/size checks, `O_EXCL`, `fchmod`/`fchown`, and an atomic link (`Sources/Helper/HelperSecurityState.swift:197-464`). The DNS listener is explicitly IPv4 loopback-only (`Sources/Helper/DNSProxy.swift:131-170`), pending DNS asks are bounded and exactly-once (`Sources/Helper/PendingDNSAsks.swift:3-49`), and blocklist text is used only as domain-set data rather than as a command or PF rule. The shipping GUI contains no web content or HTML injection sink, and no path traversal, arbitrary file write, WebView script injection, or arbitrary URL execution was found.

The coordinator's executed release evidence is affirmative: the downloaded v0.2.4 DMG had SHA-256 `97c9e7f7c0db47f97855a99c6a868940c30306178e70b64084295790ea08910f`, matching the GitHub release API and current Homebrew cask; `codesign --verify --deep --strict` succeeded; the app and helper carry Developer ID Team `H3WXHVTP97` with hardened runtime; `spctl -a -vvv -t exec` accepted them as `Notarized Developer ID`; and `xcrun stapler validate` succeeded. Both executables were universal arm64/x86_64 and linked only Apple/system libraries, with no third-party dylib or rpath payload. Mounted inspection found only the signed app and embedded helper/launchd plist—**no System Extension bundle**. `./Scripts/test_hardening.sh` passed all **18 project hardening regression checks** (with one Swift-concurrency warning), and string inspection found no obvious suspicious credential, reverse-shell, shell-download, credential-access, clipboard, camera, or keychain behavior. These checks establish authenticity and consistency for the tested artifact; they do not disprove C1–C4 because those are source-level configuration, validation, resource-control, and disclosure issues. ([release API](https://api.github.com/repos/momenbasel/purefence/releases/latest), [cask](https://github.com/momenbasel/homebrew-purefence/blob/main/Casks/purefence.rb))

## Optional Network Extension: unsafe to distribute as-is

The following findings are **confirmed in `project-netext.yml` source but do not affect the published v0.2.4 bundle**, which coordinator inspection confirmed contains no System Extension. They are ranked separately because they become shipping findings if that flavor is enabled or distributed.

| ID / severity | Status and exact location | Exploitability and impact | Specific remediation |
|---|---|---|---|
| **N1 — Medium, conditional** | The extension's XPC listener accepts every connection without a code-signing requirement: `Sources/Shared/IPCConnection.swift:79-91`. The service name is public at `Sources/Shared/Models.swift:411`. | A local process that can connect first may replace `currentConnection`, receive flow prompts, and return allow/deny decisions. The legitimate GUI connection later replaces it. The impact is firewall-policy manipulation, but exploitation depends on local Mach-service access and a connection race. | Before exporting interfaces, set a Team-ID + bundle-ID signing requirement on the incoming `NSXPCConnection`; validate the caller from the XPC audit token and reject non-Team clients. |
| **N2 — Medium, conditional** | The trusted ruleset is plain JSON in the user-writable app-group container (`Sources/Shared/SharedRuleBridge.swift:22-43`), and the extension rereads it every two seconds (`Sources/NetExt/FilterDataProvider.swift:135-142`). | A same-user process able to write the container can replace the ruleset with permissive rules or a huge payload, causing firewall bypass or memory pressure. This is conditional on access to the app-group container and on the optional extension being deployed. | Keep authoritative rules in the root helper and send a signed/authenticated snapshot over authenticated XPC. Otherwise use a protected location, atomic writes, ownership/type checks, size bounds, and an authenticated HMAC/key held outside the user-writable container. |
| **L4 — Low, optional** | `Sources/Shared/RuleMatcher.swift:28-30` treats `processPath` as a prefix, so `/usr/bin/foo` matches `/usr/bin/foobar`. | This can apply a process rule to an unintended executable. Impact is incorrect policy, not code execution. | Require exact equality or compare only at a path-component boundary. |
| **I1 — Informational** | The extension intentionally fails open if the GUI is unavailable or a decision times out (`Sources/NetExt/FilterDataProvider.swift:71-80`). | This is documented availability behavior, but it silently reduces protection and should not be mistaken for fail-closed firewall enforcement. | Surface a prominent “reduced protection/open-fail” state in the UI and system settings. |

## External supply chain, website, and repository risks

These risks concern the publisher, GitHub, Homebrew, and the documentation site rather than a direct exploit of the v0.2.4 app bytes. The most important is that **current notarization proves Apple accepted the signed bytes, not that those bytes came from the public tag**.

| ID / severity | Status and exact location | Exploitability and impact | Specific remediation |
|---|---|---|---|
| **SC1 — Medium** | **Confirmed release-provenance gap.** `Scripts/sign_and_notarize.sh:62-81` deletes `build/release`, runs XcodeGen, and builds the current working tree without checking `git status`, current commit, current tag, tag-to-commit correspondence, or a source digest. `Scripts/make_dmg.sh` packages that bundle. No workflow signs, notarizes, uploads, or publishes the release; `.github/workflows/build.yml:1-113` and `.github/workflows/release-tap-sync.yml:1-79` do not. | A dirty tree, compromised developer/release account, or erroneous manual upload can produce a notarized DMG that differs from the source users review. Users receive Apple-trusted code while provenance is absent, making a privileged-helper compromise difficult to attribute or reproduce. | Build only in CI from an exact immutable commit/tag; require a clean tree and exact `git rev-parse`/tag check; emit a build manifest and SHA-256; sign/notarize/upload only in that job; publish provenance/attestation; byte-compare the release DMG to the CI artifact. |
| **SC2 — Medium** | **Confirmed mutable-asset trust weakness in the external Homebrew tap.** The cask pins a SHA-256 but downloads `releases/download/v#{version}/PureFence-#{version}.dmg`; `homebrew-purefence/.github/workflows/bump-cask.yml:80-123` hashes whatever bytes are currently published and rewrites the cask, then pushes it at `:163-174`. The tap does not independently run Apple signature/notarization checks. | Compromise of the upstream release account, malicious maintainer action, or accidental asset replacement can eventually be blessed by the tap job. The checksum prevents silent substitution between cask updates but does not prevent the tap from adopting a replacement. Homebrew users could receive attacker-chosen code with root-helper impact after approval. | Enable immutable releases and version-unique URLs; before hashing, verify `codesign --verify --strict`, exact Developer ID/Team ID, hardened runtime, `spctl -a -vvv`, and `stapler validate`; require upstream CI provenance and an independently signed release manifest. |
| **SC3 — Medium** | **Confirmed unpinned third-party action exposure.** Local CI uses mutable `actions/checkout@v4` (`.github/workflows/build.yml:14,50`); the privileged external tap does likewise (`homebrew-purefence/.github/workflows/bump-cask.yml:30`). GitHub recommends full commit SHAs because tags can move. | **L5 — Low** | The CI build installs unpinned `xcodegen` through Homebrew (`.github/workflows/build.yml:16-20,52-56`) while `project.yml:87-101` supplies executable post-build shell phases. | Compromise of the formula, XcodeGen release, or package resolution could alter generated build phases. The values are passed through `env`, quoted, and JSON-encoded with `jq`, so no classic shell/JSON injection was found; the tap recomputes its own checksum, limiting substitution impact. | Validate with `[[ "$TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]`, construct the exact expected asset name, and verify one regular downloaded file before hashing. |
| **L7 — Low** | No GitHub artifact attestation, SBOM, reproducible-build metadata, or signed checksum manifest is produced. | This amplifies SC1 and SC2 by removing independent provenance evidence. | Produce GitHub build/release attestations, an SBOM, and a signed checksum/provenance manifest from the release CI job. |

The public website is low risk by construction: `docs/site.js:1-16` uses fixed DOM selections and writes `textContent`; there is no `innerHTML`, `document.write`, `eval`, URL construction, tracking script, analytics, third-party runtime asset, unsafe URL scheme, or confirmed stored/reflected/DOM XSS path. Two website issues remain. First, the site is stale: `docs/index.html:31,52,55,67,84-85` still identifies v0.2.2 as latest while v0.2.4 is current, potentially misleading users about release scope and migration/uninstall guidance (**Low**, documentation integrity rather than a stale-binary download because the button uses `/releases/latest`); generate the version from the release tag and add a CI mismatch check. Second, the live GitHub Pages/custom-domain response lacked CSP, `frame-ancestors`/`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, and HSTS (**Low defense-in-depth gap**, not a standalone exploit); serve a restrictive CSP and the other headers at an edge. ([stale site](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/docs/index.html#L24-L85), [live site](https://www.moamenbasel.com/purefence/))

Two additional **Low external risks** remain. First, the instructions to run `brew trust --tap momenbasel/purefence` (`docs/index.html:74-76`; `README.md:45-59`) deliberately expand trust to executable content from a third-party tap. The present cask points to v0.2.4 and pins the matching release SHA-256, so the current artifact is sound, but future tap or upstream-account compromise remains in the trust boundary; explain exactly what tap trust authorizes, publish the release checksum in user-facing documentation, and retain immutable release URLs. Second, blocklist providers are fetched over HTTPS without publisher signatures or content pinning (`Sources/Helper/BlocklistManager.swift:80-165`; seeded origins at `Sources/Shared/RuleStore.swift:119-133`). Provider compromise could cause broad false blocking or denial of service for DNS-proxy clients, but the shipping UI/XPC exposes no custom-list URL API and provider compromise was not demonstrated; document that trust, optionally verify signed digests, cap response size/count, and retain the existing last-known-good cache.

Repository history contains no suspicious deletion of security code, hidden executable binary, unexpected broad-authority contributor, dangling object, or detected committed secret. All 23 commits are unsigned (**Low repository-governance gap**, not evidence of compromise); require signed commits and verified web-flow/GitHub signing for protected branches, publish a signed release tag, and document key recovery. The one external contributor changed only `PRODUCT_NAME` and `PRODUCT_MODULE_NAME`. The history predominantly shows hardening: XPC signature/team validation, fail-closed signature handling, safer PF lifecycle handling, and removal of restricted Network Extension entitlements from the shipping build. The dormant `ip-api.com` client and `PUREFENCE_DEMO` switch are the notable suspicious-looking constructs, but both have explainable non-malicious purposes and are classified above according to their confirmed behavior.

## Overall assessment

PureFence v0.2.4 **appears suitable to run on a user's system with ordinary single-user precautions**. The tested DMG is authentic and correctly signed/notarized/stapled; the release contains no System Extension; all 18 project hardening checks passed; the XPC privileged boundary is materially sound; shell, PF-rule, SQLite-restore, and file-symlink attack paths resisted the obvious attacks; no backdoor, credential theft, unauthorized phone-home, or obfuscated payload was found. The no-telemetry/no-live-geolocation claim is credible in the inspected call graph and binary strings, although L2 is undesirable dormant code and C4 is a confirmed documentation mismatch involving MapKit.

The qualification is important because a security tool with a root helper has a large blast radius. Before treating the application as suitable for shared or high-assurance systems, fix C1 and prove the replacement scenario on each supported macOS release, add C2's DNS correlation, and bound C3's local request fan-out. Users should obtain only the official v0.2.4 DMG, verify SHA-256 `97c9e7f7c0db47f97855a99c6a868940c30306178e70b64084295790ea08910f`, install under `/Applications` rather than `~/Applications`, and not approve a helper registration from a user-writable bundle. Maintainers should not distribute the optional Network Extension flavor until N1 and N2 are fixed. Overall, the audit found **no evidence of a malicious or fundamentally unsafe shipping application**, but the current release should be considered **conditionally acceptable for low-risk personal use rather than security-hardened**.

## Scope and limitations

This was a read-only source, history, configuration, build, dependency-reference, website, and published-artifact review at commit `f53cc410a10b6474daf98b9d41980e0d6c28b1aa`; the audited repository was not modified. The analysis covered the 88-file tree, all 23 reachable commits, the shipping SwiftUI GUI and root helper, launchd/PF/DNS/SQLite/file paths, `Scripts/**`, workflows, entitlements/plists, website, optional `Sources/NetExt/**` flavor, and the independently downloaded v0.2.4 release bundle. No dynamic packet capture, launchd helper-replacement test, DNS flood/stress test, PF mutation, exploit attempt, macOS-internal BTM reverse engineering, source-to-binary reverse engineering, older-release signature review, or assessment of GitHub account MFA/branch protection/environment rules was performed. Third-party blocklist, DoH, registrar/CDN, and Apple Developer-account security were outside the direct review. These gaps explain why C1 is explicitly conditional, C4 is source-confirmed rather than packet-confirmed, and resource and provider-dependent findings are classified conservatively.
