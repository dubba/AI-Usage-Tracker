# PureFence macOS helper security audit (`Sources/Helper/**`)

Audit target: PureFence repository commit `f53cc410a10b6474daf98b9d41980e0d6c28b1aa`, read-only review of `Sources/Helper/**` plus directly relevant shared models, GUI launchd integration, build/signing configuration, and tests. No source was modified and no live helper was executed. No secrets were encountered.

## 1. What confirmed security issues exist in the privileged helper?

### Takeaway

Three confirmed weaknesses deserve remediation: the launchd job has no explicit spawn constraint and can point at a helper in a user-writable `~/Applications` bundle; the DNS proxy does not bind an upstream DNS response to the request; and the loopback DNS proxy has no query/in-flight rate limit, allowing an unprivileged local process to make the root daemon fan out unbounded upstream traffic. The launch-constraint issue is the most serious because it is a local root-code-execution defense gap after an administrator has approved the daemon.

### Cited Findings

#### C1. Confirmed configuration weakness — no `SpawnConstraint` on the root launch daemon

- **Severity:** High (conditional local privilege escalation).
- **Status:** The absence of a launch constraint is confirmed. Exact runtime exploitability on every supported macOS release was not tested because this was a read-only source audit; the supplied Apple guidance identifies this exact missing control as the defense against replacement of approved background-item code. Treat as high priority unless a live test proves an equivalent implicit `SMAppService` constraint.
- **Evidence:**
  - `Sources/Helper/Launchd.plist:12-13` selects the root daemon executable through `BundleProgram`; the complete plist has no `SpawnConstraint` (`Sources/Helper/Launchd.plist:1-25`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/Launchd.plist#L1-L25)
  - The GUI explicitly treats a user-owned `~/Applications` copy as an acceptable place from which to register the daemon (`Sources/GUI/App/HelperClient.swift:191-196`), then registers it with `SMAppService.daemon` (`Sources/GUI/App/HelperClient.swift:90-93,198-224`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/GUI/App/HelperClient.swift#L90-L93) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/GUI/App/HelperClient.swift#L191-L224)
  - The build embeds both the executable and launchd plist inside the app bundle (`project.yml:88-99`), and the helper is intended to run as a root `LaunchDaemon` (`docs/architecture.md:9-39`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/project.yml#L88-L99) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/docs/architecture.md#L9-L39)
  - Apple states that a launchd plist constraint can ensure that a registered plist runs only the expected code and specifically describes the approved-background-item replacement scenario. Apple also describes environment/launch constraints as optional, so omission must be handled explicitly. [Source](https://developer.apple.com/videos/play/wwdc2023/10266/)
- **Exploit scenario:** A standard (non-admin) user installs PureFence in their writable `~/Applications`, an administrator approves the launch daemon in Login Items, and the standard user later replaces `Contents/MacOS/PureFenceHelper` (or replaces the bundle at that path) with attacker code. If launchd has no equivalent implicit identity constraint, the next daemon start/restart executes the replacement as root. Invalidating the outer app's code signature does not itself prove that launchd will reject the embedded executable.
- **Impact:** Local privilege escalation to root, persistent root execution through the approved background item, arbitrary modification of firewall state, and a root-resident network daemon controlled by the attacker.
- **Precise remediation:** Add an explicit `SpawnConstraint` to `Sources/Helper/Launchd.plist` requiring at least `team-identifier = H3WXHVTP97` and `signing-identifier = io.moamenbasel.puresnitch.helper` (use the actual stable helper signing identifier verified from the release binary). Add a CI assertion that parses the plist and fails if `SpawnConstraint` is absent or does not bind both fields. Test replacement of the helper binary in a disposable VM and confirm a launch-constraint violation. As defense in depth, require registration from `/Applications` rather than `~/Applications`, or verify at runtime that the helper bundle and executable satisfy the expected designated requirement before exposing the Mach service. Preserve the existing unregister/re-register update path because Apple recommends re-registration after an executable or plist change. [Source](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos.md)

#### C2. Confirmed integrity weakness — DoH responses are not correlated with the DNS request

- **Severity:** Medium.
- **Status:** Confirmed missing validation; practical exploitation requires a malicious/compromised configured DoH server or a transport-security failure.
- **Evidence:** `forwardDoH` creates a request, sends the original payload, and returns any non-`nil` response body directly to the DNS client (`Sources/Helper/DNSProxy.swift:432-456`). It ignores the HTTP status and content type and never compares the response transaction ID, QR bit, question name/type/class, or answer section with the original query (`Sources/Helper/DNSProxy.swift:439-452`). The DNS parser does expose the request's transaction ID and question fields (`Sources/Helper/DNSProxy.swift:515-527`), so the necessary data is available but unused for correlation. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L432-L456) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L515-L527)
- **Exploit scenario:** The user or an administrator configures a malicious/custom DoH endpoint, or that endpoint is compromised. It returns a syntactically valid DNS response for a different transaction/question. The root proxy returns it verbatim to the waiting client rather than rejecting it as an unsolicited/mismatched response.
- **Impact:** DNS answer substitution/cache poisoning in clients that are permissive about transaction/question correlation; misleading resolution results; availability failure if an error body is returned in place of DNS.
- **Precise remediation:** Before returning an upstream body, require an HTTP 2xx response and `application/dns-message`; parse it with `DNSWire`; require `QR=1`, the exact 16-bit transaction ID, the exact normalized question name/type/class, and an opcode/response-code combination permitted for the request. Reject truncated/malformed replies. If a stricter resolver library is available, use it to validate the full response instead of the current minimal parser. Add negative tests for wrong transaction ID, wrong question name, wrong question type, non-2xx HTTP, wrong MIME type, and malformed DNS.

#### C3. Confirmed local denial-of-service weakness — unbounded DNS-to-upstream fan-out

- **Severity:** Medium.
- **Status:** Confirmed from source; no local stress test was performed.
- **Evidence:**
  - The proxy accepts loopback UDP and TCP DNS connections, with a per-listener connection limit of 128 but no per-source, per-domain, or aggregate query-rate limit (`Sources/Helper/DNSProxy.swift:131-170,250-317`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L131-L170) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L250-L317)
  - Every allowed query starts an independent `URLSession` task (`Sources/Helper/DNSProxy.swift:432-456`). There is no semaphore, task-count limit, response-size limit, or backpressure mechanism. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L432-L456)
  - A single TCP receive may contain thousands of minimal two-byte DNS-over-TCP messages because the code processes every complete length-prefixed message in the buffer before reading again (`Sources/Helper/DNSProxy.swift:291-316`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L291-L316)
  - The ask path is bounded to 256 pending decisions (`Sources/Helper/HelperService.swift:23-27,373-378`; `Sources/Helper/PendingDNSAsks.swift:3-24`), but that bound does not cover the ordinary allow/forward path. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L23-L27) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PendingDNSAsks.swift#L3-L24)
- **Exploit scenario:** Any unprivileged local process sends a high rate of valid or pipelined DNS requests to `127.0.0.1:53`. The root helper creates a correspondingly large number of outbound HTTPS tasks and buffers, consuming root-process memory, descriptors, CPU, and upstream bandwidth; a malicious DoH endpoint can return large bodies to amplify the resource cost.
- **Impact:** Root helper memory/descriptor exhaustion, disruption of firewall enforcement and monitoring, and use of the privileged daemon as a traffic amplifier toward the configured resolver.
- **Precise remediation:** Add a bounded global concurrency semaphore for outbound DoH requests, a high per-client aggregate query/token-bucket limit, a maximum number of DNS messages processed per TCP read, maximum accepted UDP payload size, and an explicit maximum upstream response size. Queue rather than immediately starting an unbounded `URLSession` task, and cancel queued tasks on `DNSProxy.stop()`. Apply conservative quotas per source address/port while recognizing that source attribution on loopback is weak; global quotas are still necessary. Add a load test asserting that a flood leaves memory and descriptor use bounded.

### Inferences

- C1 is the only reviewed condition that plausibly crosses the local-user/root boundary without first compromising an administrator credential. C2 and C3 cross into the privileged daemon's outbound-network and resource domains: a local unprivileged client can cause C3 without any XPC authority.
- The current XPC authorization is materially stronger than the launchd packaging story: once a legitimate client is connected, request authorization is explicitly enforced. C1 occurs before or outside that request-level control because launchd executes the packaged binary itself.
- The repository's launchd defense therefore depends on an OS behavior not expressed in the plist. Source-only review cannot establish whether every macOS version supplies an equivalent implicit constraint.

### Gaps

- No signed release bundle, installed BTM record, `launchd` job dump, crash report, or live macOS launch test was available. Confirm C1 in a disposable VM by replacing the embedded helper after approval and checking for `CODESIGNING 4 Launch Constraint Violation` versus root execution.
- The supported macOS range (deployment target 13.0) was not split by version for launch-constraint behavior. Verify behavior on macOS 13, 14, 15, and current releases.
- Upstream DoH-provider compromise, TLS interception, and client resolver strictness were not tested. C2's user-visible exploitability depends partly on the downstream resolver.
- Resource limits and URLSession defaults were not measured under flood conditions. C3's practical severity depends on per-task memory, response size, and upstream latency.

## 2. What potential risks exist around privileged boundaries, networking, filesystem races, and process execution?

### Takeaway

Several additional risks are conditional rather than confirmed shipping vulnerabilities: the ad-hoc build fallback weakens XPC identity checking, configurable DoH URLs lack application-level HTTPS/host restrictions, blocklist downloads have no body cap, legacy `/etc/pf.conf` migration has a narrow administrator-edit race, and root-owned cache paths rely on directory containment rather than descriptor-based symlink rejection. None provided a direct unauthenticated route to root in the reviewed release configuration.

### Cited Findings

#### P1. Potential risk — ad-hoc helper builds fall back to identifier-only XPC authorization

- **Severity:** Medium for local/ad-hoc deployments; not applicable to the Developer ID release if the signature assertions remain intact.
- **Evidence:** If the helper's signing information has no `teamid`, `clientCodeSigningRequirement()` returns only `identifier "io.moamenbasel.puresnitch"` (`Sources/Helper/HelperService.swift:302-307`). A later release check requires the configured team (`Sources/Helper/HelperService.swift:309-317`), and the release script requires a Developer ID authority and hardened runtime (`Scripts/sign_and_notarize.sh:42-52,100-106,127-130`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L302-L317) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Scripts/sign_and_notarize.sh#L42-L52)
- **Scenario/impact:** If an ad-hoc helper is manually run as root, another local program owned by the same console administrator can use a spoofed matching signing identifier to pass the listener's code requirement and race the legitimate GUI to claim the helper. The UID/admin policy still limits the peer to the console administrator (`Sources/Helper/HelperSecurityState.swift:529-579`), so this is a privilege-boundary bypass for an administrator user, not for an arbitrary standard user.
- **Remediation:** Fail closed when the helper has no trusted team identity. Put any ad-hoc development exception behind an explicit compile-time flag that cannot be present in release configuration, and never permit an ad-hoc root daemon. Retain the release-script authority/hardened-runtime checks.

#### P2. Potential risk — privileged helper accepts arbitrary DoH URL without application-level scheme/host restrictions

- **Severity:** Low to Medium; impact is primarily DNS confidentiality/integrity and root-process SSRF-like network behavior.
- **Evidence:** `setDoHUpstream` stores the client-supplied string without validation and assigns it directly to the root proxy (`Sources/Helper/HelperService.swift:873-882`). `forwardDoH` then uses `URL(string:)` only and creates the outbound request from that value (`Sources/Helper/DNSProxy.swift:432-455`). The GUI presents an unrestricted text field (`Sources/GUI/Views/SettingsView.swift:143-151`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L873-L882) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L432-L455) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/GUI/Views/SettingsView.swift#L143-L151)
- **Scenario/impact:** An accidental `http://` URL, a hostile resolver, or a URL with embedded credentials causes the root daemon to send DNS payloads to an unintended destination. The signed GUI owner is already authorized for privileged mutations, so this is not an authorization bypass; it is a dangerous configuration surface. ATS may mitigate some insecure transports, but the helper does not deliberately enforce its desired policy.
- **Remediation:** Require `https`, reject userinfo and fragments, use a deliberately small allowlist or an explicit “custom trusted resolver” confirmation, reject IP-literal/private/link-local destinations if custom resolvers are not intended, and store no URL credentials. Keep TLS at the URLSession layer and add response correlation from C2.

#### P3. Potential risk — unbounded blocklist download enables remote memory exhaustion

- **Severity:** Medium if a configured/default list provider is compromised; Low under normal trusted-provider operation.
- **Evidence:** The helper downloads a complete response with `URLSession.shared.data(for:)` and then converts the whole body to a `String` and parses it, with only a 45-second request timeout and no byte limit (`Sources/Helper/BlocklistManager.swift:80-111,142-165`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/BlocklistManager.swift#L80-L111) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/BlocklistManager.swift#L142-L165)
- **Scenario/impact:** A provider or on-path TLS failure returns a very large body, causing the root daemon to allocate it, copy it into a string, split it, and build a large set. Cached data remains active during refresh, but the refresh itself can exhaust memory.
- **Remediation:** Stream the response and abort above a documented per-list byte cap; check `Content-Length` when present; bound line/entry counts and label length; use a dedicated ephemeral `URLSession` with conservative resource limits; retain last-known-good cache only after the complete, validated new list is committed.

#### P4. Potential risk — legacy `/etc/pf.conf` migration has a check-then-replace race with another administrator write

- **Severity:** Low (availability/integrity of the system firewall configuration; requires a concurrent privileged writer).
- **Evidence:** The helper reads the live file, clones and filters it, validates the candidate, then reads the live file again and compares it to the original before `replaceItemAt` (`Sources/Helper/PFManager.swift:483-551`). The second read/comparison and replacement are not one atomic operation, so a concurrent write between them can be overwritten. The code does validate owner/mode/flags before and after replacement (`Sources/Helper/PFManager.swift:516-535,561-583`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L483-L583)
- **Scenario/impact:** A system administrator or another PF tool edits `/etc/pf.conf` during migration. The helper can replace the newer edit with its stale candidate, losing firewall configuration. This is not exploitable by an unprivileged user because `/etc/pf.conf` is root-owned.
- **Remediation:** Prefer not editing the global `/etc/pf.conf` at all; use the supported `com.apple/*` parent-anchor mechanism for current versions. If legacy cleanup remains, coordinate through a documented global PF lock, re-stat and compare the inode plus content immediately before an atomic rename, and back up/retain the original for recovery. Treat a concurrent modification as an error rather than overwriting it.

#### P5. Potential risk — blocklist cache files rely on directory containment, not descriptor-based anti-symlink operations

- **Severity:** Low.
- **Evidence:** The cache lives below the root-only support directory (`Sources/Helper/BlocklistManager.swift:22-29`; `Sources/Shared/Models.swift:427-430`). Cache reads use `String(contentsOfFile:)`, which follows a symlink (`Sources/Helper/BlocklistManager.swift:118-129`), while saves use an atomic write (`Sources/Helper/BlocklistManager.swift:132-140`). The parent support directory is checked and made `0700`/root-owned (`Sources/Helper/HelperSecurityState.swift:187-205`), but the cache directory/file themselves are not revalidated by inode, UID, type, and `O_NOFOLLOW`. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/BlocklistManager.swift#L22-L29) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/BlocklistManager.swift#L118-L140) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperSecurityState.swift#L187-L205)
- **Scenario/impact:** A malicious cache entry left from an older/insecure installation could cause the root helper to read attacker-selected file content as domain text. Because the parent is now root-only and the content only becomes blocklist domain strings, this is unlikely and does not yield code execution; it could manipulate DNS denial behavior.
- **Remediation:** Validate the cache directory with `lstat` (root owner, directory, `0700`), open cache files with `O_RDONLY | O_NOFOLLOW`, `fstat` the descriptor, and write via `open(..., O_CREAT | O_EXCL | O_NOFOLLOW)` plus `fchmod(0600)`/`fchown(0)`. Reuse the descriptor-based restore helpers or extract a shared safe-file utility.

### Inferences

- P1 matters mainly for manually run ad-hoc/root builds; the shipping script is designed to prevent that configuration.
- P2 and P3 are root-process outbound-network risks, not XPC authentication bypasses: an attacker needs influence over a trusted GUI setting or a trusted external provider.
- P4 and P5 require either privileged co-operation or pre-existing unsafe filesystem state, so they rank below C1-C3.

### Gaps

- Whether P2's `http://` and private-network cases are actually blocked by ATS in the shipped helper was not tested; no built release was available for runtime inspection.
- Default list-provider response sizes, compression behavior, and provider security posture were not assessed.
- The complete history of cache-directory ownership/permissions in older releases was not available, so P5's practical preconditions are unknown.
- Whether another privileged PF-management tool uses a lock compatible with this helper's private lock was not established.

## 3. What was checked and found sound, and what was not examined?

### Takeaway

The helper's request-level XPC authorization, command construction, PF rule interpolation, root database restoration, and cleanup gating are generally well designed and resisted the obvious command-injection, arbitrary-rule-injection, and filesystem-symlink attacks. The most important sound boundary is that each privileged XPC mutation revalidates both code identity and the current owner/admin UID rather than trusting connection establishment alone.

### Cited Findings

#### Checked and sound

- **XPC identity and per-request authorization are sound in release builds.** The listener installs a team-bound code-signing requirement (`Sources/Helper/HelperService.swift:272-318,129-130`), derives peer identity from XPC credentials (`Sources/Helper/HelperService.swift:1010-1019`), and every mutating/read method calls `authorizeCurrentXPCRequest` (examples: `Sources/Helper/HelperService.swift:587-605,618-659,684-705`). Claiming is serialized and persisted, root is excluded, the first claimant must be the active console administrator, and a claimed helper remains exact-UID/admin-only (`Sources/Helper/HelperSecurityState.swift:529-579`; `Sources/Helper/HelperService.swift:932-1005`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L272-L318) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L932-L1005) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperSecurityState.swift#L529-L579)
- **No shell-based command injection was found.** Every subprocess uses an absolute executable path and an argument array: `/bin/launchctl` (`Sources/Helper/HelperSecurityState.swift:69-87`), `/sbin/pfctl` (`Sources/Helper/PFManager.swift:756-786`), `/usr/sbin/lsof` (`Sources/Helper/NetMonitor.swift:160-173`), and `/usr/bin/nettop` (`Sources/Helper/NetMonitor.swift:310-323`). No `sh -c`, shell interpolation, or attacker-derived executable path was found. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperSecurityState.swift#L69-L87) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L756-L786) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/NetMonitor.swift#L160-L173)
- **PF rule text injection is well constrained.** Only deny rules in the `default` profile are emitted (`Sources/Helper/PFManager.swift:223-240`); domain-only and process-scoped rules are deliberately omitted (`Sources/Helper/PFManager.swift:242-275`); network tokens must pass strict canonical IPv4/CIDR validation (`Sources/Helper/PFManager.swift:305-307`; `Sources/Shared/Models.swift:132-215`); and ports are range-checked before interpolation (`Sources/Helper/PFManager.swift:277-290`). Therefore the reviewed path does not interpolate arbitrary hostname text into a root-written `pf` file. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L223-L307) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Shared/Models.swift#L132-L215)
- **The privileged database path and restore flow have strong anti-symlink/ownership controls.** The helper validates the existing database as a root-owned regular file before opening it and hardens the WAL/SHM sidecars (`Sources/Helper/HelperService.swift:63-70`; `Sources/Helper/HelperSecurityState.swift:197-217`). Restore uses `lstat` plus `open(O_NOFOLLOW)`, descriptor `fstat`, owner/type/size checks, `O_EXCL|O_NOFOLLOW` destination creation, `fchmod`/`fchown`, and an atomic `link` that refuses replacement (`Sources/Helper/HelperSecurityState.swift:219-314,316-384`). It also validates SQLite integrity and whitelists schema objects (`Sources/Helper/HelperSecurityState.swift:386-464`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperSecurityState.swift#L197-L217) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperSecurityState.swift#L219-L464)
- **The standalone root cleanup mode is gated against racing a live daemon.** It requires euid 0 and exactly one option (`Sources/Helper/main.swift:10-27`), checks that the daemon is absent through `launchctl print`, and holds the same cross-process PF lock across the absence check and cleanup (`Sources/Helper/PFManager.swift:155-185,639-665`; `Sources/Helper/HelperSecurityState.swift:42-87`). The retry path waits for daemon exit rather than assuming `launchctl remove` has completed (`Sources/Helper/PFManager.swift:167-185`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/main.swift#L10-L27) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L155-L185)
- **The DNS listener is loopback-only and lifecycle-controlled.** UDP and TCP are explicitly required to bind `127.0.0.1`, not a wildcard address (`Sources/Helper/DNSProxy.swift:131-170`), and the regression suite asserts loopback binding and LAN refusal (`Tests/HardeningRegression.swift:2273-2302`). Listener generation/state locks and per-connection timers avoid stale starts and idle TCP connections (`Sources/Helper/DNSProxy.swift:106-240,319-369`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L106-L240) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Tests/HardeningRegression.swift#L2273-L2302)
- **DNS ask settlement is bounded and exactly-once.** Pending asks are capped at 256, removal occurs under a lock, and the completion is invoked after unlocking (`Sources/Helper/PendingDNSAsks.swift:3-49`). The service also settles on timeout, client invalidation, and no-client delivery (`Sources/Helper/HelperService.swift:358-413`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PendingDNSAsks.swift#L3-L49) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L358-L413)
- **PF enable references are isolated and validated.** The helper stores only a numeric token, checks it before use, and releases only its own reference; cleanup retains the token if rule clearing/unloading fails (`Sources/Helper/PFManager.swift:327-361,667-753`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L327-L361) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/PFManager.swift#L667-L753)
- **Blocklist parsing does not feed a command or PF file.** It lowercases text, skips comments/hosts-file localhost sentinels and slash-containing entries, and the result is used only for DNS set membership (`Sources/Helper/BlocklistManager.swift:142-165`; `Sources/Helper/DNSProxy.swift:421-430`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/BlocklistManager.swift#L142-L165)
- **No OAuth tokens, authorization codes, keychain secrets, or raw provider credentials were found in the helper.** The launchd `print` output is deliberately discarded (`Sources/Helper/HelperSecurityState.swift:69-87`), and PF token failures are logged by category/exit code rather than raw token text (`Sources/Helper/PFManager.swift:756-785`). No secret value was encountered or reproduced during this audit.

### Inferences

- The codebase shows an explicit security-hardening effort: root ownership/mode checks, symlink rejection, persisted owner UID, per-call authorization, strict PF token grammar, process locking, and negative regression tests. The audit did not find an obvious shell/PF/SQL injection.
- C1 is therefore best understood as a packaging/OS-enforcement gap rather than a flaw in the helper's internal policy logic. C2-C4/C3 are runtime boundary gaps in the DNS path.
- The `SMAuthorizedClients` key embedded in `Sources/Helper/Info.plist:15-18` was not relied upon as the runtime XPC control; the helper explicitly applies its own listener code requirement. That is sound for `SMAppService` daemons, where the embedded `SMAuthorizedClients` convention is not the main runtime boundary. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/Info.plist#L15-L18)

#### Not examined / out of scope

- The optional `Sources/NetExt/**` network system extension and its separate app-group rule bridge were not audited beyond reading `Sources/Shared/SharedRuleBridge.swift`; they are not part of the shipping `project.yml` build (`project.yml:106-108`). [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/project.yml#L106-L108)
- GUI code outside the launchd/DoH crossing points was not comprehensively audited; the focus remained `Sources/Helper/**` and the shared data/protocol types it consumes.
- No Homebrew cask/repository or external installation scripts were present in the audited repository, so the exact `--cleanup` invocation and post-removal behavior were not independently verified.
- The signed/notarized release artifact, staple, BTM database record, launchd-generated job, actual file ownership/modes after installation, and runtime code signatures were not inspected. Only source and signing scripts were reviewed.
- No dynamic analysis, fuzzing, packet capture, `pfctl` execution, XPC exploit attempt, DNS flood test, launchd replacement test, or regression-test run was performed, consistent with the read-only assignment.
- macOS-internal enforcement of `SMAppService` approval, code-signature validation, background-item revocation, and any implicit spawn constraints was not reverse-engineered; Apple documentation and WWDC guidance were used as the primary external authority.
- Third-party blocklist providers' ownership, TLS posture, content integrity, and availability were not assessed.
- Platform-specific `pfctl` parser semantics beyond the helper's use of `pfctl -nf` and strict input construction were not independently verified.

### Gaps

- A final security conclusion for C1 requires a disposable-VM runtime test on each supported macOS release and inspection of the generated BTM/launchd records and crash logs.
- A definitive resource-exhaustion severity for C3 and P3 requires controlled local load testing with memory, descriptor, and network telemetry.
- Because no release artifact was provided, all signing conclusions are based on `Scripts/sign_and_notarize.sh` and build configuration rather than on `codesign` output.
- The audit did not evaluate whether the product's explicit decision to run a root DNS proxy on privileged port 53 is acceptable for the intended deployment; that is a product/security-policy decision beyond the implementation review.
