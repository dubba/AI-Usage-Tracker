# PureFence static documentation and repository-history security audit

Audit date: 2026-11-27. Scope: read-only review of `docs/index.html`, `docs/site.js`, `docs/site.css`, GitHub Pages behavior, external resources, XSS/DOM injection, URL handling, privacy/tracking, README/release consistency, and all 23 locally available commits. Repository examined at `/private/var/folders/6t/48z3q99x2jb_h8ptshks20j80000gn/T/opencode/purefence-audit`; no repository file was modified.

## Static website, GitHub Pages, XSS/DOM injection, URLs, and external resources

### Takeaway

The checked-in website is a small, static site with no dynamic HTML sinks, no third-party runtime resources, and no tracking code. The confirmed issues are a stale “latest release” presentation, missing browser hardening headers on the live GitHub Pages/custom-domain response, and a custom-DoH URL validation gap that affects the application’s privacy claim; none of the inspected website code provides a direct stored/reflected/DOM XSS path.

### Cited Findings

#### Confirmed issues

1. **Low — The public website misidentifies v0.2.2 as the latest release and embeds stale release/security-scope metadata.**
   - **Evidence:** `docs/index.html:31` declares `"softwareVersion": "0.2.2"`; `docs/index.html:52` and `docs/index.html:67` describe excluded functionality as “not included in v0.2.2”; `docs/index.html:55` labels v0.2.2 “Latest release” and links its notes; `docs/index.html:84-85` links only v0.2.2 migration/uninstall details. In contrast, `README.md:61-65` says the current name/version is PureFence v0.2.4, `project.yml:48-51` sets the app to 0.2.4/build 6, and `RELEASE_NOTES_v0.2.4.md:1-14` defines the rename release. GitHub’s live release API identifies v0.2.4, published 2026-11-27, as the latest release. [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/docs/index.html#L24-L55) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/README.md#L61-L65) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/RELEASE_NOTES_v0.2.4.md#L1-L14) [Source](https://api.github.com/repos/momenbasel/purefence/releases/latest)
   - **Exploit scenario:** A visitor follows the website’s “Release notes”/migration/uninstall links expecting current information and instead receives v0.2.2 material; search/social metadata also advertises v0.2.2. The principal download buttons do use `/releases/latest`, so this is not a stale-binary download by itself.
   - **Impact:** Users and search crawlers can make release/scope/uninstall decisions from stale information. The rename’s security-relevant migration guidance and version provenance are obscured. The v0.2.4 notes say the firewall itself was unchanged, limiting immediate technical impact.
   - **Remediation:** Make the website version/content generated or CI-validated against the latest tag; update `softwareVersion`, release labels, figure captions, and links to v0.2.4; add a CI check that rejects a site whose advertised version differs from the latest release.

2. **Low — The live GitHub Pages response lacks defense-in-depth browser security headers.**
   - **Evidence:** A 2026-11-27 response from `https://www.moamenbasel.com/purefence/` returned `200` with `server: GitHub.com`, but no `Content-Security-Policy`, `X-Frame-Options`/CSP `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, or `Strict-Transport-Security`. The repository’s HTML also has no CSP meta policy (`docs/index.html:1-42`). The live GitHub Pages hostname redirects to this canonical custom domain. [Source](https://www.moamenbasel.com/purefence/) [Source](https://momenbasel.github.io/purefence/) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/docs/index.html#L1-L42)
   - **Exploit scenario:** If an attacker can inject content into the static site or a same-origin asset is later compromised, absence of CSP and framing controls increases the usefulness of that foothold; an attacker may frame the page to place deceptive UI over the legitimate site. The current inspected markup does not itself provide the injection primitive, so this is a hardening gap, not a standalone exploit.
   - **Impact:** Reduced defense in depth and greater clickjacking/impact if a separate content-injection or compromise occurs.
   - **Remediation:** Serve the site through an edge that can set at least `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and HSTS. A CSP meta element is only a partial substitute because it cannot express every response-header policy.

3. **Low — A user-supplied “DoH upstream” is not constrained to HTTPS, despite HTTPS/DoH wording.**
   - **Evidence:** `Sources/GUI/Views/SettingsView.swift:145-151` labels the field “DNS over HTTPS upstream” and offers HTTPS examples; the field value is passed unchanged to `setDoHUpstream` at `SettingsView.swift:146-147`. `Sources/Helper/HelperService.swift:873-879` persists the arbitrary string and assigns it to the DNS proxy without scheme/host validation. `Sources/Helper/DNSProxy.swift:439-445` accepts any parseable URL and POSTs the raw DNS payload to it. The website says DNS requests go to “a DoH upstream” (`docs/index.html:80`), while `README.md:142` specifically promises a “custom HTTPS endpoint.” [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/GUI/Views/SettingsView.swift#L143-L152) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/HelperService.swift#L873-L883) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/Sources/Helper/DNSProxy.swift#L432-L456) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/docs/index.html#L78-L83) [Source](https://github.com/momenbasel/purefence/blob/f53cc410a10b6474daf98b9d41980e0d6c28b1aa/README.md#L141-L145)
   - **Exploit scenario:** A user pastes an `http://` URL—or a configuration/installer compromise supplies one—while believing the field is DoH. The root helper sends DNS query payloads to that endpoint without transport encryption. A malicious endpoint can also return arbitrary HTTP body bytes, which are forwarded as the DNS response without an HTTP status/content-type check.
   - **Impact:** Privacy leakage of queried names to an unintended endpoint, integrity weakness in returned DNS data, and a mismatch between UI/website/README claims and implementation.
   - **Remediation:** Reject every URL whose scheme is not exactly `https`; reject URL userinfo; require a valid host and port; validate the HTTP response is 2xx and its content type is compatible with DNS media types before forwarding it. If plaintext custom endpoints are intentionally supported, label them separately and warn that DNS is not encrypted.

### Inferences

- Because all website content is static and the only DOM write is `textContent`, the currently checked-in page is low-XSS-risk by construction. Future CMS/build templating or user-generated content would change that conclusion and should trigger renewed review.
- Missing response headers matter more for a security-tool download site than a purely informational page, because framing and content injection could mislead a user into approving a helper or running a command. The current page’s commands are visible and fixed, and no sensitive state exists on the page.
- The stale v0.2.2 presentation appears to result from the October website refresh not being fully updated during the November rename, rather than evidence of a malicious rollback: the October commit added the current site and the November rename changed names/links but intentionally left version-specific strings untouched. ## Repository history, contributors, deleted/renamed code, binaries, and secrets

### Takeaway

The 23-commit local history contains no suspicious deletion of security code, hidden executable binary, unexpected contributor with broad authority, or detected secret material. Security-sensitive history mostly shows hardening (XPC code-signature validation, privileged-operation authorization, safer PF handling), but every commit is unsigned and the single external contributor’s patch should be reviewed as an ordinary maintainer-contributed change rather than trusted solely because it was merged.

### Inferences

- The history pattern is consistent with iterative development by one owner with a small number of external CI/fix contributions, not with an account takeover or covert malicious contributor.
- The unsigned history and multiple author aliases reduce attribution strength, but there is no local evidence that an unauthorized actor authored the security-sensitive changes.
- The dormant geolocation actor dates to the initial release and appears to have remained unused; it is more likely dead code than an intentionally concealed exfiltration path. Deleting it would nevertheless reduce future privacy risk.

### Gaps

- Commit-signature verification could not be performed because the local environment lacked `gpg`; GitHub’s UI/API may contain additional signature metadata not present locally.
- The repository was cloned from `https://github.com/momenbasel/purefence`; remote-side branch/tag protection and release immutability are not represented in Git objects and require GitHub administrative access.
- Targeted secret scanners can miss encoded, encrypted, split, low-entropy, or unusual credential formats; no secret values were printed during this audit.
