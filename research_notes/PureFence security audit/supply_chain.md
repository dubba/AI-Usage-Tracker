# PureFence supply-chain, release, and repository-wide security audit

## 1. Release packaging, signing, notarization, dependency provenance, and artifact substitution

### Takeaway
The current v0.2.4 artifact is genuinely Developer ID-signed, hardened-runtime enabled, Apple-notarized, stapled, and accepted by `spctl`; its SHA-256 also matches both the GitHub release digest and the current Homebrew cask. No confirmed signature bypass or secret leak was found in the local release scripts. The principal weakness is **confirmed release-process provenance risk (Medium)**: releases are signed and uploaded manually from a developer's working tree, while the auto-updating Homebrew tap trusts the bytes currently published under the upstream release tag and never independently verifies Apple signature/notarization. This creates an artifact-substitution window if the upstream release account/repository is compromised or if an asset is accidentally/maliciously replaced.

### Cited Findings
- **Confirmed current-artifact integrity and signing — checked independently on 2026-11-27.** The downloaded v0.2.4 DMG had SHA-256 `97c9e7f7c0db47f97855a99c6a868940c30306178e70b64084295790ea08910f`; `codesign --verify --strict` said the DMG was valid and satisfied its designated requirement; `spctl` accepted it as `source=Notarized Developer ID`, `origin=Developer ID Application: Moamen Basel (H3WXHVTP97)`; and `xcrun stapler validate` succeeded. The mounted app and helper were also universal (`x86_64 arm64`), had hardened runtime, had the expected Team ID, and the app had a stapled notarization ticket. The GitHub release API reports the same digest and `immutable: false`; the current cask embeds the same digest. [Release API](https://api.github.com/repos/momenbasel/purefence/releases/latest) [Current cask](https://github.com/momenbasel/homebrew-purefence/blob/main/Casks/purefence.rb) [Local signing requirements](https://github.com/momenbasel/purefence/blob/f53cc41/Scripts/sign_and_notarize.sh#L42-L53) [Local post-build artifact checks](https://github.com/momenbasel/purefence/blob/f53cc41/Scripts/make_dmg.sh#L40-L61)
- **Confirmed release weakness — no provenance or tag-to-artifact binding; severity Medium.** `Scripts/sign_and_notarize.sh` deletes `build/release`, runs `xcodegen generate`, and builds the **current working tree** without checking `git status`, current commit, current tag, tag-to-commit correspondence, or a source-tree digest (`Scripts/sign_and_notarize.sh:62-81`). `Scripts/make_dmg.sh` packages that local bundle and the repository contains no workflow that signs, notarizes, uploads, or publishes the release; the only workflows are CI build and Homebrew synchronization (`.github/workflows/build.yml:1-113`, `.github/workflows/release-tap-sync.yml:1-79`). **Exploit/scenario:** a maintainer's dirty worktree, a compromised developer/release account, or an erroneous upload can produce a notarized DMG that does not correspond to the tagged source users review; users receive Apple-trusted code while provenance is absent. **Impact:** release auditing and source-to-binary correspondence are broken; a privileged-helper compromise would be difficult to attribute or reproduce. **Remediation:** build only in CI from an exact immutable commit/tag; require a clean tree and exact `git rev-parse`/tag check; generate a build manifest and SHA-256; sign/notarize/upload only in that job; publish provenance/attestation; never accept a locally produced bundle as release input without byte-for-byte comparison to the CI artifact.
- **Confirmed release weakness — Homebrew trusts a mutable upstream asset and does not verify Apple identity/notarization; severity Medium.** The cask downloads `releases/download/v#{version}/PureFence-#{version}.dmg` and pins only its SHA-256; the upstream bump workflow computes that hash from whatever bytes currently exist in the latest release and rewrites the cask (`homebrew-purefence/.github/workflows/bump-cask.yml:80-123`), then pushes it (`bump-cask.yml:163-174`). The audit gate is Homebrew style/audit, not an explicit `codesign`/Team ID/`spctl`/`stapler` verification of the DMG. GitHub's release API marks v0.2.4 `immutable: false`, so a same-named release asset can be deleted/replaced. **Exploit/scenario:** compromise of the upstream release account, malicious maintainer, or accidental replacement of the asset is eventually blessed by the six-hourly tap job; the pinned hash prevents silent substitution between cask updates but does not prevent the tap from adopting the replacement. **Impact:** Homebrew users can be redirected to attacker-chosen code; after the user approves the privileged helper, impact includes root-level code. **Remediation:** enable immutable releases; make casks point to immutable/version-unique asset URLs; in the tap job verify `codesign --verify --strict`, exact Developer ID/Team ID, hardened runtime, `spctl -a -vvv`, and `stapler validate` before hashing; require an upstream CI-produced attestation/checksum; consider an independent signed release manifest.
- **Confirmed design weakness — the upstream tap-sync payload is advisory but the validation is still too permissive; severity Low.** The tag check uses the shell glob `v[0-9]*.[0-9]*.[0-9]*` (`.github/workflows/release-tap-sync.yml:38-43`), which is not a strict numeric `vN.N.N` test. The downstream tap independently recomputes from `releases/latest` and ignores the dispatch payload's version/hash for trust decisions, which limits impact; the upstream values are nevertheless placed into environment variables, quoted, and JSON-encoded with `jq -nc`, preventing shell/JSON injection. **Exploit/scenario:** a crafted or prerelease-style tag may select an unexpected asset or fail the job, causing release synchronization denial of service. **Impact:** stale/missed Homebrew update or wrong advisory metadata; no demonstrated secret disclosure or arbitrary command execution. **Remediation:** validate with `[[ "$TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]` (or equivalent), and verify the tag is the intended latest release.
- **Confirmed safe local packaging mechanics.** Both local scripts use `set -euo pipefail`; external values are quoted; `plutil`/`codesign`/`xcrun`/`hdiutil` are invoked without a shell; recursive deletion is scoped to `build/release` or `build/dmg_staging`; `ditto` preserves bundle metadata; the DMG is signed, notarized, stapled, mounted, and checked again after packaging. No `eval`, `curl`, `wget`, `sudo`, dynamic shell construction, or secret-printing command was found in `Scripts/**`. (`Scripts/sign_and_notarize.sh:1-152`; `Scripts/make_dmg.sh:1-118`.) [Signing script](https://github.com/momenbasel/purefence/blob/f53cc41/Scripts/sign_and_notarize.sh) [DMG script](https://github.com/momenbasel/purefence/blob/f53cc41/Scripts/make_dmg.sh)
- **Confirmed dependency reference weakness — build-only XcodeGen install is unpinned; severity Low.** CI runs `brew install xcodegen` with no version/formula pin (`.github/workflows/build.yml:16-20,52-56`), while the generated Xcode project drives the build and runs a post-build shell step from `project.yml` (`project.yml:87-101`). **Exploit/scenario:** compromise of the Homebrew formula, XcodeGen release, or the runner's package resolution could alter generated build phases. The CI job has no release signing secret, so this does not directly obtain the Developer ID key. **Impact:** compromised CI output, non-reproducible builds, or compromised PR workflows; potentially higher if this unpinned step is later reused in a signing job. **Remediation:** pin an audited XcodeGen version or build it from a reviewed commit; run release builds in an isolated, minimal environment; generate a dependency/build manifest.
- **Confirmed missing release attestation; severity Low as an amplifier.** No GitHub artifact attestation, SBOM, reproducible-build metadata, or signed checksum manifest is produced. GitHub describes artifact attestations as the mechanism for establishing build provenance and supports release attestations/immutable releases. [GitHub artifact attestation guidance](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)
- **Checked-and-sound current packaging claims.** The README's statement that v0.2.4 is Developer ID-signed and Apple-notarized (`README.md:124-128`) and that the release DMG is signed/notarized (`README.md:87`) is supported by the independent v0.2.4 checks above. The shipping app's Network Extension/System Extension entitlements are deliberately absent from `project.yml` (`project.yml:57-71`), and the CI workflow checks for their absence and the exact app group (`build.yml:83-113`). [Project entitlements](https://github.com/momenbasel/purefence/blob/f53cc41/project.yml#L57-L71)

### Inferences
- Apple notarization proves Apple accepted and stapled the signed bytes, but it does **not** prove those bytes came from the public Git tag or that the release account was uncompromised. The missing tag/source binding is therefore a meaningful provenance gap rather than a flaw in the notarization step itself.
- The current cask's hash matching the current release is good present-state integrity, but the automated “download current release asset, hash it, publish that hash” pattern is not a substitute for artifact identity/provenance verification.

### Gaps
- The local repository cannot reveal whether GitHub branch protection, release-creation rules, repository settings, secret scopes/rotation, or GitHub Environment protections were enabled on 2026-11-27; those must be checked in repository/organization settings.
- The Developer ID certificate/private key, Apple notary keychain profile, and any CI signing secret were not accessible and were not inspected; only their observable output was verified.
- The current GitHub release API exposes a digest, but whether older releases/assets had different replacement histories could not be reconstructed from local git history alone.

## 2. Workflow and script injection, secret handling, action pinning, and release automation

### Takeaway
No confirmed classic GitHub Actions expression-to-shell injection was found: attacker-shaped tags and dispatch inputs are passed through `env`, expanded only as quoted shell variables, and JSON is built with `jq`. Secret references are not exposed and no real secret value was found. The main confirmed CI weakness is **unpinned `actions/checkout@v4` in privileged workflows**, including a workflow that later receives a Homebrew PAT and a tap workflow with `contents: write`; this is a **Medium supply-chain exposure**. The local scripts themselves use fixed executables/argument arrays and do not execute attacker-controlled shell text.

### Cited Findings
- **Confirmed unpinned third-party action exposure; severity Medium.** The local CI workflow uses mutable major-tag references `actions/checkout@v4` (`.github/workflows/build.yml:14,50`), and the downstream privileged tap does likewise (`homebrew-purefence/.github/workflows/bump-cask.yml:30`). The upstream release-sync workflow does not invoke `checkout`. GitHub's own secure-use reference says tags can move and recommends full-length commit SHAs or a workflow dependency lockfile. [Local CI](https://github.com/momenbasel/purefence/blob/f53cc41/.github/workflows/build.yml#L10-L17) [Tap bump workflow](https://github.com/momenbasel/homebrew-purefence/blob/main/.github/workflows/bump-cask.yml#L26-L31) [GitHub secure-use reference](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#using-third-party-actions)
- **Exploit/scenario and impact for the unpinned action:** compromise or malicious movement of the `checkout` tag/repository would execute in the tap job that has `contents: write`, permitting malicious cask changes. A `repository_dispatch` can schedule that job. The local CI workflow has no release-signing secret, so its direct impact is limited to the workflow token and runner, but a reusable compromise could become more serious if the same action/version is later used in a signing job. Separately, the upstream release-sync PAT is not exposed to `checkout`; its residual process-argument exposure is described below. **Remediation:** pin `actions/checkout` to a reviewed full commit SHA in every workflow, pin transitive actions with a dependency lockfile if available, add `CODEOWNERS` review for `.github/workflows/**`, restrict PAT scope to only the target repository and `contents: write`, rotate it periodically, and prefer a GitHub App/OIDC-like narrowly scoped mechanism where feasible.
- **Confirmed classic workflow-injection mitigation is sound.** The upstream sync passes `inputs.tag` and the release tag through `env` as `INPUT_TAG`/`EVENT_TAG`, assigns them from quoted variables, writes them to `$GITHUB_OUTPUT` in a grouped block, constructs JSON with `jq -nc --arg`, and passes JSON as one quoted `-d` argument (`.github/workflows/release-tap-sync.yml:24-52,55-78`). This follows GitHub's recommended intermediate-environment-variable mitigation. The repository history explicitly changed this in commit `51f8934` to remove direct `${{ }}` interpolation from the shell body. [Workflow](https://github.com/momenbasel/purefence/blob/f53cc41/.github/workflows/release-tap-sync.yml#L24-L79) [GitHub injection guidance](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#mitigating-the-risk-of-script-injection-attacks)
- **Potential residual shell/pattern issue; severity Low.** Although untrusted values are not interpolated into the script text, the permissive `case` glob remains (`.github/workflows/release-tap-sync.yml:38-41`) and the derived asset name is passed to `gh release download --pattern`. A crafted release tag may therefore affect asset-pattern selection or cause job failure. The tap recomputes its own trusted checksum, so this is not a demonstrated checksum-substitution path. **Remediation:** strict numeric validation, expected exact asset-name construction, and verify the downloaded local file is exactly one regular file before hashing.
- **Confirmed least-privilege soundness in the upstream sync, with one caveat.** The workflow's own `GITHUB_TOKEN` has `contents: read` (`.github/workflows/release-tap-sync.yml:17-18`); the cross-repository operation uses a separately named secret `TAP_DISPATCH_TOKEN` (`release-tap-sync.yml:55-59`), and the script does not print it. `curl` uses a fixed `https://api.github.com/...` URL, `--fail-with-body`, `-sS`, a quoted JSON payload, and no shell interpolation (`release-tap-sync.yml:69-78`). **Potential caveat, Low:** the bearer token appears in curl's process arguments on the ephemeral runner; use a curl config/stdin or environment-driven header mechanism if local process observation is in the threat model. GitHub warns that automatic secret redaction is not guaranteed and recommends least privilege and masking.
- **Confirmed no secret leakage found.** Repository-wide searches for AWS keys, GitHub tokens, private-key headers, API-key/password assignments, and common secret formats found no real secret values. `TAP_DISPATCH_TOKEN` and `github.token` are references only; the `424242` value in tests is explicitly a fake pf reference token, not an authentication credential (`Tests/HardeningRegression.swift:91-160,2209-2229`). `.gitignore` excludes `.env`, `.env.local`, `*.p12`, `*.cer`, `*.mobileprovision`, and `notary_password.txt` (`.gitignore:31-37`). [Git ignore](https://github.com/momenbasel/purefence/blob/f53cc41/.gitignore#L31-L37)
- **Confirmed unsafe `curl`/shell usage not found in local release scripts.** `Scripts/**` contains no `curl` or `wget`; the only `curl` is the fixed GitHub API dispatch above. The local scripts invoke `plutil`, `codesign`, `xcrun`, `hdiutil`, `ditto`, `mktemp`, `lipo`, `spctl`, and `swift` with quoted fixed arguments and no command-string construction. `Scripts/make_icon.sh:14-101` writes a fixed, reviewed Swift program to a private `mktemp` directory and passes only the output path as an argument.
- **Confirmed PR/build trust boundary is reasonably separated, with supply-chain caveat.** CI runs on `pull_request` and `push` to `main` (`build.yml:3-8`), not `pull_request_target`; it checks out the PR merge/head and builds with signing disabled (`build.yml:22-32`). No repository secret is exposed to that job, and no privileged `pull_request_target`/`workflow_run` pattern exists. However, `brew install xcodegen` is unpinned and `project.yml` contains executable post-build shell, so a malicious PR can execute arbitrary shell in the ordinary CI runner as intended for compiling/testing; it cannot obtain signing secrets from this workflow. **Remediation:** explicitly set `permissions: contents: read`, pin XcodeGen, avoid unnecessary network/package installation, and retain separation between validation CI and signing/release CI.
- **Confirmed tap-side command construction is guarded.** The tap's Python rewrite accepts version only when it matches `[0-9]+(\.[0-9]+)*` and SHA only when it matches `[0-9a-f]{64}`, and requires exactly one replacement of each field (`homebrew-purefence/.github/workflows/bump-cask.yml:98-123`). It independently downloads the latest release asset and hashes it rather than trusting the dispatch payload (`bump-cask.yml:32-96`). The external tap also refuses a downgrade (`bump-cask.yml:56-68`). This is sound against dispatch-payload hash substitution.
- **Confirmed release-sync trigger design is permissive but not immediately exploitable.** It fires on every published release and manual dispatch (`.github/workflows/release-tap-sync.yml:8-15`); the PAT can request a dispatch to the tap. A malicious publisher with upstream release rights could cause repeated sync jobs, but the tap independently chooses the latest release and the script contains no release-authorizing code. **Impact:** CI/PAT use and possible update churn/DoS. **Remediation:** restrict release creation to protected maintainers, add rate/concurrency limits, and use an environment-protected publishing process.

### Inferences
- Passing untrusted values through `env` is the correct GitHub Actions injection boundary. The remaining concern is input semantics (glob validation), not expression injection.
- A PAT with write access to the Homebrew tap is a high-value credential. SHA-pinning the action and narrowing/rotating the PAT materially reduces its blast radius.

### Gaps
- GitHub Actions logs, runner image contents, organization runner policies, and actual secret/PAT scopes were unavailable; a PAT may have broader permissions than the comment claims.
- The current contents and commit provenance of `actions/checkout@v4` were not independently audited action-by-action; pinning should be to a locally reviewed known-good SHA.
- Repository branch protection, required reviewers, tag protection rules, environment approval requirements, and GitHub's “immutable releases” feature status could not be verified from the checkout.

## 3. Repository-wide backdoor indicators, hardcoded URLs/secrets, eval-like execution, shell construction, and network claims

### Takeaway
No backdoor, credential theft mechanism, eval-like interpreter, obfuscated payload, dynamic shell construction, or unauthorized phone-home was found in the current tree or reachable git history. The documented outbound behavior (enabled blocklist downloads; optional loopback DNS proxy forwarding to a user-selected DoH endpoint) matches code. Two discrepancies deserve attention: a **dormant `ip-api.com` geolocation client is compiled into both shipping binaries even though it is unused** (Low latent privacy/supply-chain risk, not demonstrated runtime leakage), and the helper accepts arbitrary DoH URLs without enforcing HTTPS despite the UI calling this “DNS over HTTPS” (Low policy/privacy weakness).

### Cited Findings
- **Confirmed no active live-geolocation call, but dormant network client remains; severity Low / latent risk.** `Sources/Shared/IPGeo.swift:3-42` defines an `IPGeoCache` actor that sends the queried IP to `https://ip-api.com/json/{ip}?...` (`:15-26`). `Sources/Shared` is compiled into both GUI and helper targets (`project.yml:41-44,150-166`), and strings in the independently downloaded v0.2.4 GUI and helper binaries contain `https://ip-api.com/json`. A whole-tree symbol search found no caller of `IPGeoCache.shared`, `lookup`, or `IPGeoCache`; the Network Monitor explicitly documents the geolocation path as unused (`Sources/GUI/Views/NetworkMonitor.swift:177`). Therefore the README/release claims that the current release **does not perform live IP-geolocation requests** are behaviorally accurate (`README.md:133,234,278`; `RELEASE_NOTES_v0.2.2.md:70-73`). **Impact:** no observed traffic today, but dormant privileged code contains an external geolocation endpoint and could be accidentally activated in a future change; it also complicates source/binary privacy review. **Remediation:** remove `IPGeo.swift` from shipping targets or delete it, and add a regression test asserting no shipped source contains an unapproved egress endpoint.
- **Confirmed DoH endpoint is not constrained to HTTPS; severity Low / potential privacy issue.** The Settings text field passes arbitrary user text to `setDoHUpstream` (`Sources/GUI/Views/SettingsView.swift:143-151`); the root helper stores and applies it with no URL scheme/host validation (`Sources/Helper/HelperService.swift:873-882`); the DNS proxy accepts any parseable URL and POSTs the raw DNS wire payload to it (`Sources/Helper/DNSProxy.swift:432-455`). The documented examples are HTTPS (`README.md:141-142`), but an `http://` URL is not rejected. **Exploit/scenario:** a user or a caller with authorized GUI access configures an HTTP or attacker-controlled endpoint; DNS queries are disclosed or manipulated. This is user-configured custom-upstream behavior, not an unauthenticated remote exploit, and XPC authorization limits callers. **Impact:** plaintext DNS disclosure or malicious DNS answers for manually proxied clients. **Remediation:** require `https`, reject userinfo/non-HTTP schemes, show the resolved host prominently before applying, warn on changed endpoints, and ideally pin/allowlist known public resolvers while retaining an explicit advanced custom-host mode.
- **Confirmed expected network destinations only.** The helper's live egress paths are: (1) enabled blocklist downloads (`Sources/Helper/BlocklistManager.swift:31-115`), whose eight seeded HTTPS origins are explicit in `Sources/Shared/RuleStore.swift:119-133`; (2) the optional DoH POST (`DNSProxy.swift:432-455`); and (3) the dormant, uncalled IP geolocation client described above. No analytics, crash-reporting, telemetry SDK, advertising SDK, or phone-home code was found. The README's network claim is otherwise consistent (`README.md:124,186-190,230-235,278`). [Blocklist fetcher](https://github.com/momenbasel/purefence/blob/f53cc41/Sources/Helper/BlocklistManager.swift#L31-L115) [Seeded list origins](https://github.com/momenbasel/purefence/blob/f53cc41/Sources/Shared/RuleStore.swift#L119-L133)
- **Potential blocklist supply-chain risk; severity Low.** Third-party list content is fetched over HTTPS without publisher signatures or content pinning, and parsed into the domain set (`BlocklistManager.swift:80-165`). The shipping UI/XPC exposes no custom-list URL API, so ordinary users cannot turn this into arbitrary URL fetching; list-provider compromise could nevertheless cause broad false blocking or denial of service for DNS-proxy clients. **Impact:** availability/privacy (DNS queries to a malicious/compromised DoH provider), not code execution. **Remediation:** document trust in list providers, optionally verify signed digests, cap response size/count, and fail safely to the last-known-good cache (the latter already exists: `BlocklistManager.swift:33-69,118-140`).
- **Confirmed no eval-like execution, obfuscation, or dynamic shell construction.** Searches over all tracked source, scripts, workflows, docs, and every reachable git revision found no `eval`, `new Function`, JavaScript `eval`, `system`, `popen`, `dlopen`, `osascript`, AppleScript, runtime shell decoding, Base64-encoded payload, XOR/cipher, or obfuscated command construction. Swift subprocesses use `Process.executableURL` plus an argument array: fixed `/sbin/pfctl` (`Sources/Helper/PFManager.swift:757-785`), fixed `/usr/sbin/lsof` and `/usr/bin/nettop` (`Sources/Helper/NetMonitor.swift:162-164,311-313`), and fixed `/bin/launchctl` (`Sources/Helper/HelperSecurityState.swift:69-79`). There is no shell interpreter and no user-controlled executable path. [PF process invocation](https://github.com/momenbasel/purefence/blob/f53cc41/Sources/Helper/PFManager.swift#L756-L785) [Monitor process invocation](https://github.com/momenbasel/purefence/blob/f53cc41/Sources/Helper/NetMonitor.swift#L155-L170)
- **Confirmed no unauthorized DNS listener exposure.** The privileged helper binds UDP and TCP DNS explicitly to IPv4 loopback (`Sources/Helper/DNSProxy.swift:126-159`), consistent with `README.md:141-142,320`. The launchd daemon is associated with the PureFence bundle (`Sources/Helper/Launchd.plist:4-19`). The helper is not sandboxed and runs as root, so these controls remain important; no wildcard listener was found in source.
- **Confirmed no hardcoded real secret.** The only credential-like literals are public identifiers (Team ID `H3WXHVTP97`, bundle IDs), fake test tokens, and secret *references*. No private key, bearer token, API key, password, notary credential, or Apple keychain-profile secret is embedded. The notary profile is only a local keychain profile name (`Scripts/sign_and_notarize.sh:8-10`; `Scripts/make_dmg.sh:12-14`).
- **Confirmed hardcoded URLs are limited and explainable.** In shipping code they are Apple DTD/schema URLs, GitHub/help links, Cloudflare/Quad9/Google DoH examples, seeded blocklist URLs, and the dormant `ip-api.com` endpoint. Historical scans showed no removed/renamed hidden endpoint or suspicious redirect. The documentation website links to the author's ordinary public site and GitHub/release locations (`docs/index.html:9-38,51-89`), not to a telemetry or payload host.
- **Confirmed documentation drift, not a vulnerability.** The landing page still labels v0.2.2 as “Latest release” and links its notes (`docs/index.html:55`), while the repository's latest tag/API release is v0.2.4; its download button correctly points at `releases/latest` (`docs/index.html:51`). Some older release notes retain old `puresnitch` GitHub URLs, which GitHub redirects. **Impact:** users may read stale capabilities/limitations and have reduced confidence in release metadata. **Remediation:** update landing-page release version and canonical links as part of release automation.
- **Checked-and-sound repository hygiene.** The tracked tree contains only 88 files and no vendored binary executable, package manager manifest, Swift package dependency, generated Xcode project, or checked-in private credential; `.gitignore` excludes common secrets, generated projects, builds, and archives. Git history is short and attributable to the maintainer plus two named contributors; no unreachable suspicious object was reported by `git fsck` in the inspected clone. The `.gitignore` does exclude `*.zip`, `*.app`, `*.dmg`, `artifacts/`, and `build/`, preventing accidental release artifact commits. [Ignore rules](https://github.com/momenbasel/purefence/blob/f53cc41/.gitignore)
- **Checked-and-sound suspicious-construction searches.** A regex sweep covered hardcoded URLs/secrets, `eval`/`exec`/`system`/`popen`, shell interpreters, Base64, AppleScript, `curl`/`wget`, `URLSession`, `NWConnection`/`NWListener`, `Process`, and privilege-related command strings across the whole repository; findings were manually reconciled to the expected blocklist, DoH, dormant geolocation, system-tool, and CI paths above. Historical sweeps across all reachable commits did not reveal an additional hidden endpoint, encoded payload, or suspicious command.

### Inferences
- The combination of a root helper, XPC, `pfctl`, DNS, and external list/DoH endpoints gives the codebase substantial blast radius if a single input-validation or release-provenance control fails. The observed code generally uses fixed executable paths and argument arrays, so shell injection is not the dominant risk; release/account integrity and DNS-upstream trust are more material.
- The dormant geolocation actor is not evidence of a backdoor because it has no callers and the UI explicitly says geolocation is not performed. Its inclusion is nevertheless avoidable privacy-sensitive dead code in a privileged binary.

### Gaps
- Dynamic network behavior was not captured with a packet trace or DNS proxy during a full helper lifecycle; source review and binary string inspection cannot prove that an unusual runtime path never issues a request.
- Third-party blocklist contents, their publishers' controls, and the current behavior of each DoH provider were not independently audited.
- Apple Developer team membership, certificate history/revocation, provisioning profiles for the non-shipping Network Extension flavour, and the exact identity/permissions of the notary keychain profile were not accessible.
- The GitHub Actions organization/repository policy, PAT actual scopes, audit logs, release-download logs, and historical asset replacement history were not available.
- `docs/NETWORK-EXTENSION.md` describes a non-shipping Developer ID flavour requiring two provisioning profiles and a separate signing flow (`docs/NETWORK-EXTENSION.md:33-55`); that flavour was not built or distributed in the inspected v0.2.4 release, so its future packaging/provenance cannot be certified by this audit.
